# Planning request: Visual four-agent software development framework

I want you to work with me in planning mode to design a local application that orchestrates four prompt-defined agents, displays their data flow in a graphical interface, and lets me run one cycle, a specified number of cycles, or continuously until I stop it. Develop a detailed, implementation-ready plan. Do not begin implementation during this planning conversation.

The sections below capture my intended capability. Distinguish firm requirements from proposed implementation choices and unresolved questions. Preserve the firm requirements. Ask targeted questions in manageable groups, explain meaningful tradeoffs, and recommend defaults where appropriate. Do not ask me to repeat decisions already specified here. Inspect the existing repository and applicable project instructions if one is available before proposing a file structure or implementation approach.

## 1. Overall intent and technology direction

Use Python with LangGraph as the preferred orchestration framework. The purpose is to have a reusable framework rather than four separately hard-coded agent implementations. Each agent's responsibilities and behavioral instructions should primarily come from an editable Markdown prompt file. Shared infrastructure should handle model access, invocation context, artifact handling, events, scheduling, and cancellation.

The application should show exactly four visible agent nodes:

1. System Engineer
2. Software Engineer
3. Tester
4. Marketing

The application must support parallel work where dependencies permit it, with predictable ordering where dependencies require it. Separate the four visible agent identities from the internal execution steps needed to implement the workflow correctly. An agent may execute more than once in one cycle.

Validate the proposed LangGraph approach against current official documentation during planning. In particular, explain how the selected APIs implement fan-out, fan-in, repeated invocations of the same logical agent, streaming events, and cancellation. Do not assume that simply drawing multiple incoming edges guarantees the execution behavior described here. If additional scheduling or cancellation infrastructure is necessary, explain its purpose and keep it as small as practical.

The GUI technology is not yet decided. Recommend an appropriate local desktop or locally hosted browser approach and ask me to confirm the choice. Explain the practical implications for installation, responsiveness, graph rendering, prompt editing, streaming, and shutdown. I commonly work on Windows, so confirm the target operating systems and make Windows setup explicit if selected.

Put the four role prompts in a separate `prompts/` folder. Use these proposed filenames unless there is a specific reason to adjust them:

- `prompts/system_engineer.md`
- `prompts/software_engineer.md`

Provide a configuration file that defines the agents. Recommend a human-editable format, such as YAML or TOML. At minimum, configuration should map stable agent IDs to display names, prompt paths, and output folders. Explain where graph relationships, invocation modes, and execution settings belong. Ask whether the graph itself needs to be configurable in the first version or whether it should initially use the fixed workflow below.

Keep the framework's implementation code separate from the generated product. Do not accidentally treat `src/product/` as the framework's own source tree. The initial implementation should include substantial starter prompts for all four roles. ## 4. Agent responsibilities

### System Engineer

The System Engineer is the starting agent for every cycle. Its first input includes my Master Prompt / Vision. It defines or updates requirements for the desired software capability and places its artifacts in `src/requirements/`.

Requirements should be useful to both implementation and testing. Propose a practical format with stable requirement identifiers, acceptance criteria, and unresolved assumptions. Ask whether such a format should be enforced or simply encouraged by the prompt.

When this agent finishes successfully, its requirements are available to the Software Engineer, Tester, and Marketing.

### Software Engineer

The Software Engineer receives the requirements and the Master Prompt / Vision as context. It creates or updates the actual software in `src/product/`. It should receive relevant existing product files when iterating on an existing result.

When it finishes successfully, its software output is available to the Tester and Marketing. Its handoff should identify what changed, which requirements it attempted to satisfy, and any known limitations or setup instructions.

### Tester

The Tester has two distinct responsibilities within the same visible role:

1. After receiving requirements from the System Engineer, write or update test cases and relevant use cases.
2. After receiving the Software Engineer's completed output, test the software and produce results.

Both activities are driven by `prompts/tester.md`. A structured invocation field may distinguish activities such as `prepare_tests` and `execute_tests`; this does not create a fifth visible agent or require a second Tester prompt file.

The test preparation activity can run in parallel with software development. Test execution must wait until the software and the required test preparation are ready. Do not let test execution race with test-file creation or evaluate an incompletely written product.

The Tester must produce actual test evidence where execution is supported, rather than claim that tests passed based only on an LLM's inspection. Distinguish test planning, test generation, test execution, and result interpretation. Capture failures, skipped tests, execution errors, and limitations honestly. Clarify the product language and test runner before finalizing how tests execute.

### Marketing

Marketing receives the requirements, software information, and testing information, together with the Master Prompt / Vision. It produces a file or files under `src/ads/` that explain and help sell the feature.

The materials should reflect what was actually implemented and tested. Unsupported capabilities, failing tests, and unverified claims must not silently become statements of completed functionality.

Ask what form I want initially, such as a Markdown feature brief, product announcement, or sales summary. A Markdown feature brief is a reasonable proposed default. Clarify whether Marketing runs once after all inputs are ready or updates its output each time an upstream input arrives.

## 5. Required visible graph

| --- | --- | --- |
| System Engineer | Software Engineer | Requirements for implementation |
| System Engineer | Tester | Requirements for test preparation |
| System Engineer | Marketing | Requirements and feature intent |
| Software Engineer | Tester | Software ready for testing |
| Software Engineer | Marketing | Implementation information |

The graph within a cycle is a directed acyclic graph. Repeating the workflow happens through an outer cycle controller, rather than adding a visible backward edge that contradicts that graph.

Lay out the nodes so the direction of work and all six arrows are easy to follow. Keep exactly four visible nodes even if the runtime uses additional internal steps, barriers, or invocation records. Avoid overlapping labels, obscured arrowheads, and activity previews that cover important connections.

## 6. Execution semantics that must be resolved explicitly

My original concept is that an agent can run more than once when different incoming paths trigger it. A cycle is one full traversal of the workflow, including all parallel branches and all work triggered during that traversal. It is not simply one model call per visible node.

Before finalizing the plan, resolve these distinctions with me:

- Does each incoming edge cause an independent invocation, or can some incoming edges supply context to a single invocation that waits for all required inputs?
- Tester should prepare tests from requirements and subsequently execute tests against the product. How will those two activities be represented internally?
- Does Marketing run once after all three sources are ready, or incrementally as each source completes?
- If Tester emits both a test plan and final test results, which of these traverse the Tester-to-Marketing edge, and which trigger Marketing?
- If the same logical agent executes multiple times, do its downstream deliveries happen for every invocation or only for designated output events?

Recommend a deterministic initial interpretation for discussion: System Engineer completes; Software Engineer and Tester test preparation run in parallel; Tester execution waits for both; Marketing produces its final artifact after current-cycle requirements, implementation information, and test results are available. Under that interpretation, some visible arrows represent data delivery rather than immediate model invocations. This is a proposed default to confirm, not a substitute for my request to support repeated agent invocations.

Show an execution trace using concrete invocation IDs so I can see exactly which steps run, which overlap, and what data reaches each invocation. If you recommend another interpretation, show its trace and explain why.

Define cycle completion using explicit runtime state: all required invocations have finished, all required handoffs have been delivered, no scheduled work remains, and no active branches remain. Do not infer cycle completion from node colors or from all four agents having run at least once. A stopped or failed partial traversal is not a successfully completed cycle.

Prevent duplicate scheduling and unintended exponential cascades. Tag state, inputs, outputs, and events with run, cycle, agent, and invocation identifiers. Explain how parallel branches merge their results without overwriting unrelated state and how downstream steps avoid mixing artifacts from different cycles.

## 7. Master Prompt / Vision

Place a clearly labeled multiline text field at the top left of the GUI:

**Master Prompt / Vision**

This contains the overall task or product vision. It is the starting input to the System Engineer and shared context for every other agent. Role prompts define responsibilities; the master prompt defines what the team is trying to accomplish.

Plan how the master prompt is saved and restored across application launches. Ask whether saving is automatic or explicit. Also resolve whether edits during execution are disabled or staged for a later cycle. Never allow different agents in a cycle to receive inconsistent versions accidentally.

Recommend capturing a consistent snapshot of the master prompt, role prompts, and relevant configuration for each cycle or run. Clarify exactly when newly saved prompt edits take effect, especially during continuous execution.

This prompt should be sourced from `prompts/vision.md` file.  It should be editable and have a save button as well.

## 8. Cycle controls

At the top of the interface, provide:

- **Process 1 Cycle**: starts one complete workflow traversal.
- A positive integer field, initially `1`, paired with **Process X Cycles** or an equivalently clear label.
- **Process Until Stopped**: continues starting new cycles until I stop execution or a defined failure condition occurs.

While any run is active, disable all start controls and the cycle-count input so I cannot accidentally start overlapping runs. Keep an obvious Stop control available during execution; a prominent bottom control is acceptable. Continuous mode may also change its button to a Stop presentation, but the result should remain unambiguous.

Show current execution status, current cycle number, and completed cycle count. For finite runs, make progress toward the requested total clear. Validate the cycle count and explain why starting is unavailable when required configuration or the master prompt is missing.

Clarify what happens between cycles. Repeating the same master prompt should have a defined purpose. Ask whether subsequent cycles refine the existing artifacts using previous test results, regenerate the product, or follow another policy. Recommend a deliberate iterative policy, with prior-cycle feedback supplied as context at the next cycle boundary. Keep that separate from the within-cycle DAG. Do not invent unlimited autonomous repair loops inside an agent invocation.

## 9. Immediate Stop is a firm requirement

I explicitly want an immediate halt when I press Stop. Do not implement Stop as "finish the current agent" or "finish the current cycle."

Plan cancellation across the full stack:

- Stop scheduling new invocations and handoffs immediately.
- Cancel active asynchronous tasks and close active response streams or requests where supported.
- Stop any running local test processes, including child processes where necessary.
- Prevent late responses or queued events from advancing the graph or modifying accepted artifacts after cancellation.
- Hide the transient processing previews and update node states promptly.
- Mark the run or partial cycle as stopped/cancelled, not completed.
- Preserve valid outputs that were already committed and avoid accepting partially written outputs as complete artifacts.
- Remain responsive while cancellation cleanup happens and reject overlapping starts until cleanup is safe.

Be honest about remote-provider limitations: stopping local processing may not terminate computation already underway at the service. Define immediate halt in terms of local scheduling, local processes, stream handling, and artifact acceptance, and explain any provider-specific cancellation support separately.

Ask what a new Start action means after a stop: restart the interrupted cycle, begin a fresh cycle using the last accepted artifacts, or resume from a checkpoint. Recommend the simplest reliable first-version behavior. Resume/checkpoint recovery is not automatically required.

## 11. Processing indicators and compact live previews

When an agent is actively processing, show a clear visual highlight around its node, such as an outline, halo, or restrained animation, together with a status indicator.

Below that agent, display a small transient window showing live activity. It should be approximately the width of the node and a similarly compact footprint, with small text as requested. It must appear only while the agent is processing and disappear when the agent is no longer processing, including completion, error, and cancellation.

If possible, show a compact rendering of the interaction with the model API: a sanitized input summary, streamed response excerpts, tool activity, or actual test execution output. This should be real activity, not fabricated "thinking" text. Do not require or imply access to a model's private internal reasoning. Public response text, explicit progress summaries, and observable execution events are sufficient.

Plan bounded buffers, throttled rendering, and sensible scrolling so large responses do not freeze the UI. Keep credentials and sensitive headers out of previews. If streaming is unavailable, display honest status such as "Waiting for model response" and then an output excerpt while the invocation remains active.

When multiple agents run concurrently, show each active node and its own preview. If multiple invocations of one agent can overlap, propose either serialization for that role or a clear way to represent multiple active invocations without adding permanent nodes. Clarify whether optional expandable details are useful; do not replace the requested compact default with a large console.

## 12. Edge traversal feedback

At the beginning of a cycle, untraversed arrows should appear light gray. When a handoff traverses an edge, recolor it visibly so I can watch the cycle progress. Define the traversal event precisely, preferably successful delivery of the source output to the destination's input state, rather than merely starting a source model call.

If a destination waits for additional inputs, its incoming delivered edge can be colored while the node itself remains waiting. This distinction should be understandable.

For multiple cycles, reset the edge state at the cycle boundary. Consider alternating completed-edge accent colors between cycles to make the transition visible, as I suggested. Keep the active cycle number visible so color is not the only indication. If an edge can carry more than one handoff within a cycle, explain how a second traversal is signaled without falsely implying another cycle completed.

Use text or icons as well as color to distinguish idle, waiting, running, completed, failed, and cancelled states where those distinctions matter. Keep the default interface focused on the master prompt, execution controls, four-node graph, transient previews, and concise status.

## 13. Artifacts, context, and tools

Specify how model responses become real files. Evaluate structured artifact responses, constrained file tools, or another concrete mechanism. The framework should be able to identify every output's destination, validate it, and report persistence errors. Do not rely on a free-form response being treated as a successfully written file.

Plan a shared context contract that includes:

- The master prompt and the agent's role prompt.
- The invocation's specific activity and triggering inputs.
- Relevant current requirements, product files, tests, and results.
- Existing artifacts and previous-cycle feedback when the chosen iteration policy requires them.
- Output conventions and the authorized output directory.

Do not blindly include every prior token or every file forever. Describe a practical bounded-context approach and how larger artifacts are selected or referenced.

Resolve artifact overwrite/version behavior. Explain how current artifacts are updated, how failed or cancelled invocations are prevented from publishing incomplete file sets, and how downstream agents read consistent accepted versions. Atomic writes or staged output commits are useful candidates. Keep any durable agent-generated artifact history under `src/` if retained; distinguish that history from framework runtime metadata.

Constrain file access to the selected workspace and appropriate role outputs. Reject path traversal and prevent generated outputs from overwriting the framework or `.env`. Test execution must use a defined execution boundary and timeout. Ask whether a subprocess, container, or another environment is appropriate for my machine and intended product. Explain that a working directory alone is not a security sandbox.

The Software Engineer and Tester may need command execution, dependencies, or tool-assisted model loops. Ask what tools are required and what "one completed agent invocation" should mean. Recommend bounded tool use with explicit limits if it is necessary; do not silently turn each graph step into an unbounded autonomous agent.

## 14. Runtime state and failure handling

Define clear run, cycle, invocation, and handoff records. Propose an event contract that supports GUI updates without coupling rendering directly to model clients. Events should carry identifiers, timestamps, status, and sanitized preview content or artifact references as needed.

Consider events for run start, cycle start, invocation queued/started, streamed output, artifact commit, handoff delivered, invocation completion/failure/cancellation, cycle completion, and run termination. Exact event names are implementation choices.

Resolve error policy explicitly:

- Does an invocation failure stop the whole run, only its downstream branch, or trigger a bounded retry?
- Are ordinary failing product tests treated as a valid Tester result, while runner crashes and infrastructure errors are failures of the invocation?
- Can Marketing summarize known failing tests, and can the next cycle attempt improvements?
- How are retries prevented from duplicating outputs or downstream work?
- What happens on application close, a lost GUI connection if using a browser, or a process crash?

Recommend fail-fast behavior for unrecoverable orchestration failures and explicit bounded retries for suitable transient provider failures. Keep Stop available during retry backoff. Do not mark a failed dependency as successfully traversed to make the graph look complete.
